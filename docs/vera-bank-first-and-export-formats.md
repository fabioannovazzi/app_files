# Bank-first reconciliation and accounting export formats

The normal `run-all` reconciliation route and raw open-item preparation use one
source-bound bank-first orchestrator. The optional purpose is `bank_open_items`,
`bookkeeping_check` or `audit_reconciliation`; it changes the assignment context,
not the process or its accounting controls.

The existing strict matcher files remain intermediate candidate evidence for
compatibility and replay. The final route reads the **whole normalized bank and
journal population**, not only their unmatched residual, and never restores an
old zero-difference group as an established bank fact. Before reserving any cash
evidence, the common orchestrator applies its explicit versioned admission rule:
nonempty source reference and party, known currency/unit/entity, signed direction,
exact cents, admitted complete group/date scope, no duplicate source signatures.
Amount/date candidates remain context and do not consume evidence. Open-item
strong admissions additionally reuse the established source-replayed exact-match
eligibility checks and the existing domain allocation validator.

Every other primary case goes to the actual native low-cost worker. Every doubt
left by it, including missing documents, goes to the actual stronger native worker.
Both stages examine bank questions first, then secondary accounting questions.
On Codex these stages select advertised Luna and Sol configurations from the
owned policy using the existing subscription capsule. Cowork and Antigravity
retain their actual native model selection and completion receipts. Missing
capabilities are technical errors, never fictitious execution or a paid API fallback.
Format retries stay in their own stage. Sources, policy, preceding conclusions,
requested/observed model evidence and attempt artifacts bind resume; completed
calls are not repeated. CLI self-report is not provider attestation.

`bank_resolution` and `accounting_resolution` are separate. An evidenced ATM
withdrawal can resolve cash-out while its cash-box/owner allocation stays open.
An unidentified RiBa/effects total stays a primary doubt even when an invoice
amount coincides. Established bank facts are carried unchanged into secondary
analysis. Confirmed differences stay explicit findings. Candidate examination,
reserved cash evidence, exact allocation, invoice closure and TeamSystem partita
identity are distinct; amount equality or an internal number cannot establish
the latter facts. Source, direction, currency/entity, policy, partial-payment,
non-reuse and residual controls apply equally to both semantic stages.

Open-item packets explicitly declare `settlement_magnitude` as their comparison
basis. Positive matching magnitudes never imply cash-in: original source amounts,
debit/credit fields and `source_cash_amount` retain the bank direction for model
review. The receiving domain still validates the supplied accounting side and
allocation policy. Its native panel reads the producer’s existing nested review
location, so it shows the same canonical questions as the workbook.

Primary counters partition the same bank movements into deterministic, Luna,
Sol, human, error and unprocessed. Accounting counts overlap and are never added
to that total. Only actual residual questions after the stronger worker enter
the human queues. JSON, workbook and native read-only outcome section share these
results; saved human choices and private drafts remain separate and unchanged.
Opening a panel does not run models or recalculate a client case.

## Export adapters

`posting_export_formats.py` defines `vera.reviewed_journal_entry.v1`: source
movement, date, explicit saved accounts, debit/credit, exact decimal amounts and
namespaced supplied external references. Balanced **accepted saved accounting
lines** are the export input. Bank resolution alone is not export eligibility.
Reconciliation never writes an export or silently accepts an operator's choice.

The versioned adapter registry owns the destination label, standard/version,
filename extension, encoding, required profile and encoder. Each additional
adapter validates the same neutral journal contract and its own destination
requirements before any file is written. Unsupported or unconfigured targets
fail without creating output or altering choices. Receipts name the exact
adapter and retain the source decisions hash; importing remains a separate act.

- `teamsystem_imppn_v1`: available, TXT TeamSystem, Formato IMPPN, CP1252,
  fixed positions and exact original optional partita/year/section behavior.
- `datev_koinos`: target prepared; verified DATEV Koinos / DATEV Italia receiving
  import specification/configuration required. German DATEV EXTF is not assumed.
- `zucchetti`: target prepared; receiving product, version and verified import
  specification required. No generic Zucchetti CSV is claimed.

The existing native proposal editor currently uses TeamSystem account/reference
validation. A new destination must provide its own acquired chart and field
profile when that editor is extended; the neutral journal contract and adapter
boundary do not fabricate destination account mappings. DATEV Koinos documents
configurable text-file bank/cash intake, which does not by itself establish a
universal accounting-posting layout:
https://studi.datev.it/datev_resources/INFORMAZIONI_DK/extcnt/Contabilita/Datev.IT.Contabilita.Contabilita.pdf

## Validation boundary

Fixtures are synthetic. Package/browser tests do not establish native installed
Codex visual acceptance, model accuracy, real-client acceptance or compatibility
with a customer's TeamSystem, DATEV Koinos or Zucchetti installation. No private
139-movement experiment or its counts are shipped or treated as a production rerun.
No Marketplace publication, cache replacement, real-case export or import is part
of this release.

### Explicit manual samples and final delivery

Normal bank-first runs retain the legacy sample as diagnostic data. A caller can
explicitly request it with the boolean assumption `manual_review_sample: true`;
this preserves the established source-bound manual-review, decision and
regeneration path. It does not create completed decisions or professional
approval. The option is declared run configuration in output lineage.

A complete, replay-validated bank-first result with every in-scope item closed
and no requested manual sample can pass the final review gate without creating
human review records. Unresolved items, incomplete model review and explicit
manual review remain gated. The run date is established before exact admission.
